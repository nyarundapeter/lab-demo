# BioTest Diagnostics4.0

A working, three-app demo of a diagnostic-lab platform, built on the DBP
Blueprint factory pattern: one generated backend (technician-facing
servicing workspace) plus two independently-deployed, hand-built thin
clients (patient self-service, and a referring-clinician portal). BioTest
itself never diagnoses or treats — only the referring doctor does; this
platform gets a patient or referral registered, tracked, and released.

## The three apps

| App | Path | Port | Who it's for | Built how |
|---|---|---|---|---|
| Servicing Workspace | [`apps/dws-07`](apps/dws-07) | 3000 | Technicians, front desk (internal) | Generated by the DBP factory (`scaffold-solution.mjs`), exported standalone |
| Patient App | [`apps/patient-app`](apps/patient-app) | 3001 | Patients booking their own visit | Hand-built Next.js, no generator |
| Partner Portal | [`apps/partner-portal`](apps/partner-portal) | 3002 | Referring doctors / front-desk staff | Hand-built Next.js, no generator |

Only `apps/dws-07` talks to the platform services (auth, RBAC, data, audit,
notifications). The two client apps have zero platform-service access of
their own — every read and write proxies through a single seam file
(`lib/biotest-client.ts`) over HTTP to `apps/dws-07`. This asymmetry is
deliberate, not an oversight — see [`docs/01-Architecture/01.2-High-Level-Design/hlad-v1.0-draft.md`](docs/01-Architecture/01.2-High-Level-Design/hlad-v1.0-draft.md)
AD-08 ("DWS-hub / DXP-thin-client topology").

```
┌─────────────────┐        ┌──────────────────────┐
│   Patient App    │──HTTP─▶│                        │
│  (port 3001)     │        │   apps/dws-07          │
└─────────────────┘        │   (port 3000)          │
┌─────────────────┐        │   PS.AUTH · PS.RBAC     │
│  Partner Portal  │──HTTP─▶│   PS.DATA · PS.AUDIT    │
│  (port 3002)     │        │   PS.NOTIF · PS.SEARCH  │
└─────────────────┘        └──────────────────────┘
```

## Running it locally

Each app is independently run and installed — start `dws-07` first, the
client apps have nothing to call until it's up.

```bash
# 1. Backend
cd apps/dws-07 && pnpm install && pnpm --filter @dbp/app-dws-07 dev   # :3000

# 2. Patient App
cd apps/patient-app && npm install && npx next dev -p 3001            # :3001

# 3. Partner Portal
cd apps/partner-portal && npm install && npx next dev -p 3002         # :3002
```

Both client apps read `BIOTEST_BASE_URL` from `.env.local` (defaults to
`http://localhost:3000`) — copy `.env.example` to `.env.local` in each if
missing.

## Personas at a glance

- **Patient** — self-service account (name/email/phone/password), books a
  visit directly, tracks it in My Bookings.
- **Referring clinician** (`consultant` or `front-desk`, [`apps/partner-portal`](apps/partner-portal)) —
  two flat, descriptive roles with identical rights (no hierarchy); refers a
  patient on the patient's behalf, tracks it in My Referrals filtered by
  their own account, not by patient phone.
- **Technician** — releases an exam order in a single action once complete;
  there is no internal approval gate before release (AD-02).

## Known limitations (interim, tracked)

- No database provisioned yet (`BIOTEST-G-01`) — all three apps use
  in-memory storage; data resets on restart.
- No trusted-caller shared-secret guard on `apps/dws-07`'s PS.DATA route
  yet — the client apps send `x-dbp-internal-key`, but nothing checks it.
- No separate patient-visible vs. referrer-visible publish-scope field on
  `lab-service` — both client apps filter on `status: active` only.
- No automated tests written yet for either client app.
